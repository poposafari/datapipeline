# PopoSafari 데이터 파이프라인: 아키텍처와 기술 선택의 근거

> 작성 기준: 2026-09-08, 현재 `datapipeline` 코드와 저장소의 기존 운영 기록.
> 목적: 무엇을 만들었는지보다 **어떤 제약에서 무엇을 선택했고, 무엇을 포기했는지** 설명한다.
> 이번 문서 작성 중 미니 PC에 SSH 접속하거나 운영 부하를 측정하지 않았다.

## 1. 설계를 한 문장으로 요약하면

**게임 서버의 분석 부하를 분리하고, 기존 로그 아카이브를 미니 PC에서 증분 적재한 뒤, 검증된 집계 결과를 정적 대시보드로 제공하는 배치 분석 시스템이다.**

중요한 것은 “작은 서버라서 큰 도구를 못 썼다”가 아니다. 현재 작업은 입력 경로와 실행 순서가 단순하고, 조회 화면도 정해져 있다. 따라서 분산 인프라를 먼저 추가하기보다 **데이터 정확성, 재실행 안전성, 게시 일관성에 복잡성을 투자**했다.

단, 사용자가 제시한 “로그를 실시간으로 보고 싶다”는 요구는 이 구조만으로 충족하지 않는다. 이번 구현 범위는 서버 변경 없이 `datapipeline` 내부 최적화와 대시보드 개선까지다. 실시간 요구를 없앤 것이 아니라, 서버 개발자와 수집 계약을 정해야 하는 다음 설계 과제로 남겨둔 것이다.

## 2. 사실과 판단의 구분

| 구분 | 이 문서에서의 취급 |
| --- | --- |
| 현재 구현 | 이 저장소의 셸·SQL·Python·브라우저 코드로 확인한 동작 |
| 기존 운영 기록 | 기존 문서에 기록된 하드웨어, 서버 아카이브 방식, 저장소 정책. 현재 원격 상태를 재확인한 것은 아님 |
| 설계 판단 | 확인된 구조와 제약을 바탕으로 한 비용·효과 분석 |
| 향후 제안 | 아직 구현하거나 합의하지 않은 개선안과 도입 조건 |

특히 기존 [architecture.md](architecture.md)에는 이전 설계 설명이 남아 있다. 다음 항목은 현재 코드 및 [README](../README.md)를 기준으로 읽어야 한다.

- 백업은 하드링크가 아니라 **체크포인트 후 독립 파일 복사**다. 하드링크는 이전 DB 내용을 보존하는 백업이 아니다.
- 대시보드는 집계값뿐 아니라 **`account_id`도 포함**한다. 익명 공개 화면으로 취급하면 안 된다.
- 증분 처리는 ID 중복 방지에 더해 **처리 완료 객체 이력**을 사용한다.
- 정적 대시보드 빌드는 지표별 별도 조회가 아니라 **하나의 DuckDB 연결·트랜잭션**에서 수행한다.
- Metabase와 Superset을 모두 JVM 기반이라고 묶는 설명은 부정확하다. 이 문서의 비교 근거는 언어 이름이 아니라 상시 구성요소와 운영 요구다.

## 3. 요구사항과 작업 범위

### 3.1 해결하려던 문제

1. DAU, 신규 가입, 포획 결과, 미끼·돌 사용, 사파리 체류시간을 확인한다.
2. 차트의 숫자에 참여한 계정을 확인하고 검색한다.
3. 반복 실행에서 이미 처리한 로그를 불필요하게 다시 읽지 않는다.
4. 적재·빌드 실패 시 데이터가 부분 반영되거나 정상 화면이 사라지는 일을 막는다.
5. 운영 게임 서버에 분석 쿼리나 신규 분석 서비스를 추가하지 않는다.

### 3.2 이번에 해결하지 않은 문제

- 이벤트 발생 후 수 초 이내 화면 반영을 보장하는 실시간 수집.
- 서버의 로그 생성·아카이브·삭제 로직 수정.
- 다중 사용자 인증, 계정별 조회 권한, 공개 인터넷 서비스.
- 미니 PC 장애에도 지속되는 고가용성 구성.
- 운영 데이터 규모에서의 최대 처리량·지연시간 보장.

이 경계를 명시하지 않으면 “대시보드가 자동 갱신된다”를 “실시간 파이프라인이 완성됐다”로 오해하게 된다.

## 4. 미니 PC 사양과 설계에 미친 영향

### 4.1 저장소에 기록된 사양

출처는 [계획 v2의 미니 PC 항목](data-pipeline-plan-v2.md)과 [계획 v3의 하드웨어 항목](plan-v3-data-pipeline.md)이다. 아래 RAM·디스크 수치는 **당시 관측값**이며 현재 여유량이 아니다. 단위도 기존 기록을 따랐다.

| 항목 | 기록된 값 | 아키텍처 관점 |

| 물리 디스크 | 111.8G, 기록상 LV 확장 여지 약 55G | 논리 볼륨 밖 공간은 현재 파일시스템의 가용 공간이 아님 |

사용자가 제공한 접속 대상은 `mori@poposerver-mini-pc`, 서비스 경로는 `/opt/poposafari-data-pipeline/dashboard/public`, 실행 사용자는 `mori`다. 기존 문서의 장비명은 `poposafari`이므로, 동일 장비인지와 사양 변경 여부는 배포 전 확인해야 한다. 호스트 이름만으로 OS 배포판이나 디스크 종류를 확정하지 않는다.

현재 사양을 확인하려면 해당 장비에서 다음 읽기 전용 명령을 실행할 수 있다.

### 4.2 왜 상시 서비스 수를 줄였는가

배치 분석은 하루 중 일부 시간에만 CPU·메모리를 집중적으로 사용한다. 그런데 스케줄러·브로커·캐시를 모두 상시 운영하면 **분석하지 않는 시간에도 관리 대상과 자원 경쟁이 남는다.**

현재 구조는 적재와 빌드가 끝나면 해당 프로세스가 종료된다. 파이프라인이 추가하는 상시 애플리케이션은 정적 파일 서버이며, cron·systemd 같은 OS 서비스는 별도로 존재한다. 차트 렌더링은 접속한 사용자의 브라우저가 수행한다.

서비스 유닛의 `MemoryMax=128M`은 **정적 파일 서버의 제한값**이지 DuckDB 적재·빌드 메모리 사용량도, 실측 RSS도 아니다. 이 숫자로 “파이프라인 전체가 128MB만 쓴다”고 설명하면 안 된다. [서비스 유닛](../dashboard/serve/poposafari-dashboard.service)

### 4.3 RAM보다 먼저 놓치기 쉬운 디스크 비용

운영 공간에는 최소한 다음 항목이 함께 들어간다.

```text
현재 DB + 직전 DB 사본(.prev)
+ 백업 교체 도중의 임시 사본
+ WAL·쿼리 임시 공간
+ 새 대시보드 생성 공간 + 보관 중인 상세 데이터 버전
+ OS와 운영 로그 + 안전 여유 공간
```

기존 `.prev`가 있는 상태에서 새 백업을 먼저 복사하므로, 교체 순간에는 대략 DB 세 사본 규모가 필요할 수 있다. 파일시스템에 따른 복사 최적화를 보장으로 간주하지 않는다. 따라서 “37G가 남았으니 데이터 37G까지 저장 가능하다”는 계산은 잘못이다.

Kafka 보관 로그나 Redis 영속화 파일까지 같은 디스크에 얹는 경우, 평상시 사용량뿐 아니라 재시작·재처리·파일 재작성 시점의 피크도 함께 검토해야 한다. 이 프로젝트에서는 그 추가 비용을 정당화할 요구가 아직 구현 범위에 없었다.

## 5. 전체 구조와 책임 분리

```text
[운영 게임 서버 — 이번 작업의 변경 대상 밖]
  사용자 행동 → 애플리케이션 → PostgreSQL audit_log
                               │
                               └─ 기존 아카이브 작업
                                      │ gzip JSONL 업로드
                                      ▼
[기존 외부 저장소]
  R2: audit/YYYY/MM/DD/audit-<stamp>-<cutoff>.jsonl.gz
                                      │ 읽기 전용 접근
                                      ▼
[미니 PC — datapipeline]
  cron → load/run.sh → 객체 스캔·미처리 객체 선택
                       → DuckDB wh.audit + 처리 이력
                       → 정제 뷰·지표 뷰·품질 검사
       → dashboard/build.sh → 동일 DB 스냅샷으로 집계·상세 생성
                             → 검증 → 버전 상세 파일 게시
                             → snapshot.json 원자 교체
       → 정적 HTTP 서버 → 운영자 브라우저의 Chart.js

  별도 cron → checks/reconcile.sh → R2와 로컬 대사
```

| 위치 | 맡는 일 | 맡지 않는 일 |
| --- | --- | --- |
| 게임 서버 | 이벤트 생성, 서비스 트랜잭션, 원본 아카이브의 정확성 | 대시보드 요청마다 분석 집계 실행 |
| R2 | 아카이브 보관, 재처리를 위한 파일 전달 경계 | 이벤트 브로커, 소비자 offset 관리, 차트 실시간 push |
| 미니 PC | 증분 적재, 정제·집계, 품질 확인, 화면용 파일 생성 | 이미 서버에서 잃어버린 이벤트 복원 |
| 브라우저 | 렌더링, 기간 선택, 유저 상세 검색·페이지 이동 | 원본 DB 접속, 집계 정본 생성 |

기존 문서상 운영 서버는 게임과 PostgreSQL이 함께 있는 Lightsail 4GB·2vCPU 버스터블 인스턴스다. 이 역시 현재 원격 확인값은 아니다. 설계상 중요한 점은 분석을 서비스 DB에서 반복하면 서비스 자원과 경쟁한다는 것이다. **분리의 목적은 분석 속도뿐 아니라 게임 응답시간에 영향을 주는 경로를 줄이는 것**이다.

## 6. 핵심 설계 결정과 트레이드오프

### 6.1 DuckDB + SQL 뷰: 분산보다 로컬 분석에 맞추기

원본을 `wh.audit`에 저장하고, 방어적 파싱과 지표 계산을 뷰로 분리했다. 현재의 중심은 raw 테이블과 뷰이며, 일반적인 raw·staging·mart 세 계층을 모두 영구 테이블로 복제하지 않았다.

- **얻는 것:** 변환 규칙을 SQL로 추적하고, 파생 테이블 동기화와 저장 공간을 줄인다.
- **지불하는 것:** 뷰 조회 시 계산 비용이 발생한다. 객체 적재가 증분이라고 지표 계산까지 완전한 증분 집계인 것은 아니다.
- **재검토 조건:** 데이터가 늘어 전체 집계가 실행 시간 예산을 넘으면 병목 지표부터 물리화하거나 날짜별 재계산을 설계한다.

DuckDB에 스캔 과금이 없다는 이유만으로 계산이 공짜가 되는 것은 아니다. 현재는 지속적인 다중 사용자 DB 요청을 제거하고, 빌드 시간에 계산을 모아 이 비용을 통제한다. [적재 스키마](../load/00_schema.sql), [정제 뷰](../views/00_audit.sql), [지표 뷰](../views/20_metrics.sql)

### 6.2 객체 이력 + 행 ID: 서로 다른 중복 문제를 해결하기

ID 중복 방지만으로는 결과가 중복되지 않을 뿐, gzip 파일을 다시 다운로드하고 파싱하는 낭비는 남는다. 그래서 두 단계를 구분했다.

1. `wh.loaded_objects`로 성공적으로 읽은 경로를 제외한다.
2. 객체끼리 겹치는 행은 `id` 기준으로 중복 반영을 막는다.
3. 로그 행·객체 처리 이력·적재 로그를 같은 트랜잭션에서 커밋한다.

실패했는데 완료 이력만 남으면 재시도 때 파일을 건너뛰므로, **완료 기록과 데이터의 원자성이 재실행 안전성의 핵심**이다. 이는 애플리케이션 수준의 멱등 처리이지, 전체 이벤트 경로의 exactly-once 보장은 아니다.

평소에는 최근 7일을 대상으로 하고, 오래 중단됐으면 마지막 성공 적재일을 기준으로 범위를 넓힌다. 경로 날짜는 이벤트 발생일이 아니라 아카이브일이므로 이벤트 날짜만으로 객체를 고르지 않는다.

이 방식은 완료 객체가 불변이라는 가정이 있다. 같은 경로의 내용이 변경되면 일반 실행은 알아채지 못한다. `FORCE_RELOAD=1`은 현재 스캔 창을 다시 읽고 기존 ID도 갱신하지만, 창 밖의 모든 과거 파일을 재처리하거나 소스에서 사라진 ID를 삭제하지 않는다. 또한 현재 객체 탐색은 넓은 glob 후 필터링이므로 **객체 본문 재읽기 감소와 R2 LIST 비용 제거는 다른 이야기**다. [스캔 로직](../load/05_scan.sql), [적재 로직](../load/10_load_audit.sql)

### 6.3 로컬 파일 잠금: Redis 없이 실행 충돌 제어

적재는 배타 잠금, 빌드와 대사는 공유 잠금을 사용한다. 충돌 시 무한 대기하거나 겹쳐 실행하지 않고 종료 코드 75를 반환한다. 빌드 출력 경로에도 별도 잠금이 있다.

한 장비·한 DB를 대상으로 하기 때문에 로컬 파일 잠금이 범위에 맞는다. Redis 분산 락을 넣으면 락 만료와 갱신, 네트워크 단절 같은 새로운 실패 조건이 생기지만 지금 해결할 다중 호스트 경쟁은 없다.

대신 이 잠금은 협조적이다. 래퍼를 통하지 않는 수동 SQL이나 다른 경로로 같은 DB를 여는 프로그램까지 모두 제어하는 장치는 아니다. 코드 75 자체도 자동 재시도를 예약하지 않으므로, 실패 알림 후 재실행 또는 다음 스케줄에 의존한다. [잠금 구현](../load/locked.py)

### 6.4 정적 JSON: 요청마다 계산하지 않기

운영자가 동일한 네 차트를 볼 때마다 DB 쿼리를 다시 실행할 이유가 적다. 집계 결과를 미리 파일로 만들어 두면 조회 경로에서 DB 연결과 동적 API를 없앨 수 있다.

- 적재·빌드가 잠시 실패해도 이전에 게시한 화면은 남는다.
- 사용자 수 증가가 곧 집계 SQL 실행 횟수 증가로 이어지지 않는다.
- 운영 서버에 Node나 프런트엔드 빌드 체인을 추가하지 않는다.
- 대신 사용자가 임의 조건으로 무제한 분석하는 동적 BI 기능은 제공하지 않는다.

현재 HTTP 서버는 신뢰할 수 있는 내부 운영자용의 최소 구성이다. 인터넷 공개나 다수 사용자 서비스를 위한 보안·성능 설계를 완료했다는 뜻은 아니다.

### 6.5 원자적 게시: 숫자의 시점을 맞추기

집계 JSON과 유저 목록을 따로 만들면, 빌드 중 DB가 바뀌거나 파일 일부만 교체되어 서로 다른 시점의 데이터를 보여줄 수 있다.

해결 순서는 다음과 같다.

1. 하나의 읽기 트랜잭션에서 집계와 기여 계정을 계산한다.
2. 게시 경로와 같은 파일시스템의 임시 디렉터리에 파일을 만든다.
3. 스키마와 필수 값을 검증한다.
4. 고유 `build_id`를 가진 상세 디렉터리를 먼저 게시한다.
5. 마지막에 `snapshot.json`을 `os.replace`로 교체한다.

새 화면은 단일 스냅샷을 기준으로 읽고, 상세 패널은 처음 열었던 빌드 ID를 유지한다. 이로써 정상 실행 중 부분 게시가 노출되는 문제를 줄인다. 호환용 개별 JSON 전체가 하나의 파일시스템 트랜잭션으로 교체되는 것은 아니며, 정전까지 포함한 완전한 게시 내구성을 입증한 것도 아니다. [빌드 구현](../dashboard/build.py), [계약 검증](../dashboard/contract.py)

### 6.6 유저 상세: 계산 의미와 로딩 비용을 함께 설계

“이 값의 유저”는 지표마다 의미가 다르다. DAU는 활동 계정, 성공 건수는 성공으로 역산된 시도의 계정, 성공률은 분모에 포함된 시도의 계정이다. 중앙값·p90은 완료 세션의 참여 계정을 보여주는 것이지 “중앙값을 만든 한 사람”을 찾는 기능이 아니다.

포획 성공은 원본 이벤트의 연결 키 부족 때문에 기존 지표에서 역산한다. 상세에도 같은 의미를 유지하고, 실제 성공 로그와 동일하다고 단정하지 않는다. 식별자가 없는 기록은 별도로 표시한다.

성능상으로는 툴팁에 최대 10명만 넣고, 전체 목록은 날짜·지표별 파일을 클릭할 때 가져온다. ID를 문자열로 전달하고 검색과 50명 단위 페이지 이동을 제공한다.

**페이지 이동은 브라우저 내부 처리다.** 전체 상세 파일을 50명씩 서버에서 나눠 받는 방식은 아니다. 한 날짜에 수십만 계정이 모이면 해당 파일의 전송·메모리 비용이 커질 수 있고, 빌드도 상세 결과를 메모리에 읽는다. 그때 파일 분할이나 인증된 상세 API를 검토해야 한다. [상세 생성](../dashboard/drilldown.py), [상세 UI](../dashboard/public/drilldown.js)

## 7. Airflow·Kafka·Redis를 넣지 않은 이유

### 7.1 먼저, 세 도구는 한 세트가 아니다

| 도구 | 주된 역할 | 도입해도 자동으로 해결되지 않는 것 |
| --- | --- | --- |
| Airflow | 작업 의존성·스케줄·실행 이력을 관리하는 오케스트레이션 | 서버의 실시간 이벤트 발행, 차트 렌더링 |
| Kafka | 이벤트 전달·보관·소비자 분리·재생을 위한 스트리밍 기반 | 지표 정의, DB와 발행 사이의 원자성, 조회 API |
| Redis | 캐시·공유 상태·메시징 등 선택한 자료구조에 따른 기능 | 로그 정본과 분석 웨어하우스의 자동 대체 |

따라서 “실시간 차트니까 셋 다 필요하다”는 결론은 성립하지 않는다. 수집 지연, 계산 지연, 조회 지연 중 실제 병목을 먼저 정해야 한다.

### 7.2 Airflow: 실행할 수 없어서가 아니라 작업 그래프가 단순해서

현재 핵심 흐름은 `적재 → 빌드`이며, 대사는 별도 스케줄이다. 선행 성공 조건은 셸의 `&&`, 이력은 `wh.load_log`, 중복 실행 방지는 파일 잠금, 실패 확인은 로그·알림으로 나눠 처리한다.

Airflow를 넣으면 DAG 단위 실행 가시성, 작업별 재시도, 복잡한 의존성 관리에 이점이 있다. 반면 Airflow 3 계열의 기본 구조에는 스케줄러·DAG 프로세서·API 서버·메타데이터 DB 등의 역할이 추가된다. 분산 워커나 Redis가 언제나 필수인 것은 아니고, 단일 장비 구성도 가능하다. [Airflow 아키텍처](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/overview.html)

공식 Docker Compose 안내는 Docker에 최소 4GB, 가능하면 8GB의 메모리를 할당하도록 안내한다. **이는 예제 구성에 대한 안내이며 “모든 Airflow 설치가 최소 4GB를 상시 점유한다”는 뜻은 아니다.** 다만 약 7.7GB 장비에서 예제를 그대로 도입할 때 분석 작업과 함께 자원 예산을 검토해야 한다는 근거는 된다. [Airflow Docker 안내](https://airflow.apache.org/docs/apache-airflow/stable/howto/docker-compose/index.html)

이 프로젝트의 판단은 다음과 같다.

- DAG 관리의 편의보다 새로운 DB·서비스·업그레이드·장애 조사 경로의 비용이 현재 더 크다.
- Airflow를 넣어도 DuckDB 쿼리 자체나 R2 아카이브 도착 주기가 빨라지지 않는다.
- 서버가 로그를 내보내지 않으면 Airflow 스케줄만 촘촘하게 해도 새로운 데이터는 없다.

**포기한 것:** 작업별 자동 재시도·백필 UI·통합 DAG 이력 관리. cron이 Airflow와 동등한 기능을 제공한다고 주장하지 않는다.

**도입을 재검토할 때:** 독립 파이프라인과 의존성이 늘어나고, 날짜 구간별 재처리·부분 재실행·여러 운영자의 작업 추적을 셸로 유지하는 비용이 커질 때다. 이 경우 현재 스크립트를 Airflow task에서 호출하는 방식으로 실행 제어부터 옮길 수 있다.

### 7.3 Kafka: 파일 수집 경계만 바꿔서는 실시간이 되지 않아서

Kafka는 생산자가 이벤트를 기록하고 여러 소비자가 독립적으로 읽으며, 보관된 이벤트를 다시 소비하는 구조에 적합하다. 현재 입력은 이미 만들어진 R2 gzip 파일이고, 분석 소비 경로도 단순하다. [Kafka 소개](https://kafka.apache.org/41/getting-started/introduction/)

`R2 → Kafka → DuckDB`만 추가하면 파일 도착 전까지의 지연은 그대로다. 오히려 파일 분해·발행·offset·적재 이력이라는 관리 대상이 추가된다. 기존 R2는 현재 배치에서 재처리 가능한 전달 경계 역할을 하지만, Kafka의 스트리밍·소비자 그룹·역압력 기능과 동등한 대체재는 아니다.

실제로 이벤트 발생 직후 Kafka로 보내려면 서버 측 설계가 필요하다.

- 서비스 DB 커밋과 이벤트 발행 사이에 실패하면 어떻게 복구할 것인가?
- outbox 또는 CDC 같은 방식이 필요한가?
- 이벤트 ID와 스키마 버전, 순서 범위, 재전송·중복 제거 규칙은 무엇인가?
- 미니 PC가 꺼졌을 때 이벤트는 어디에 얼마나 보관되는가?

이 문제는 `datapipeline` 폴더에 브로커 설정을 추가하는 것만으로 해결되지 않는다.

하드웨어 측면에서도 Kafka는 JVM heap만 계산하면 안 된다. OS 파일 캐시, 보관 로그, 디스크 쓰기, 소비자 처리 비용까지 같은 장비에서 경쟁한다. 단일 노드 실행은 가능하지만 **같은 미니 PC에 브로커를 여러 개 띄워도 장비·디스크 장애 도메인은 하나**다. Kafka의 분산 내구성을 그대로 얻는다고 설명할 수 없다.

현대 Kafka는 KRaft 구성이 있으므로 “Kafka를 쓰려면 ZooKeeper까지 반드시 설치해야 한다”는 주장도 맞지 않는다. 공식 문서는 broker/controller 결합 모드를 개발 환경에 사용할 수 있으나 중요한 운영 배포에서는 피하도록 안내한다. [Kafka KRaft 운영 문서](https://kafka.apache.org/41/operations/kraft/)

**포기한 것:** 저지연 이벤트 전달, 독립 소비자 확장, offset 기반 스트림 재생을 현재 제공하지 않는다.

**도입을 재검토할 때:** 실시간 지연 목표가 합의되고, 분석·알림·탐지 등 독립 소비자가 생기며, 장애 중 버퍼링과 재생이 실제 요구가 될 때다. 운영할 별도 장비·관리형 서비스·보관 정책도 함께 결정해야 한다.

### 7.4 Redis: 현재 조회 경로에 캐시할 동적 쿼리가 없어서

Redis는 세 도구 중 소규모로 시작하기 쉬운 선택일 수 있다. 따라서 “미니 PC라 Redis도 무거워서 못 쓴다”는 설명은 핵심을 놓친다.

현재 대시보드 요청은 이미 계산된 파일을 읽는다. 정적 JSON 자체가 재사용 가능한 계산 결과이므로, 앞에 Redis를 추가해도 요청마다 반복되던 집계 SQL을 줄이는 효과는 없다. 이미 그 SQL이 조회 경로에 없기 때문이다. 대신 적재 완료와 캐시 갱신 시점을 맞추는 문제가 추가된다.

용도를 구분하면 더 분명하다.

| Redis 사용안 | 현재 제외한 이유 |
| --- | --- |
| 집계 캐시 | 정적 스냅샷이 계산 결과 재사용을 이미 수행 |
| 분산 락 | 단일 호스트·단일 DB라 로컬 잠금으로 범위 충족 |
| Pub/Sub 실시간 알림 | 서버 발행과 수신 서비스가 없고, 전달 누락을 허용할지도 미정 |
| Streams 이벤트 버퍼 | 전달 보장·재처리·보관 정책을 설계해야 하며 현재 파일 수집의 직접 대체가 아님 |

Redis Pub/Sub은 at-most-once 의미를 가지므로 구독자가 끊긴 동안 메시지를 나중에 되살려 받는 로그 정본으로 사용하면 안 된다. Streams는 별도의 소비·보관 기능을 제공하므로 Pub/Sub과 혼동하지 않아야 한다. [Redis Pub/Sub 문서](https://redis.io/docs/latest/develop/pubsub/)

또한 Redis에는 RDB·AOF 영속화가 있다. “Redis는 메모리라 무조건 전부 사라진다”도 틀린 설명이다. 다만 영속화를 선택하면 저장 주기·쓰기 비용·복구 동작을 운영해야 한다. [Redis 영속화 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

**포기한 것:** 여러 API 인스턴스의 공유 캐시·공유 상태와 실시간 fan-out을 제공하지 않는다.

**도입을 재검토할 때:** 동적 API가 생기고 동일 질의 반복이 실제 병목이 되거나, 여러 인스턴스 사이에서 상태·실시간 알림을 공유해야 할 때다. 그때도 정본인지 재생성 가능한 캐시인지 먼저 결정한다.

### 7.5 종합 판단

> Airflow·Kafka·Redis의 미도입은 성능 한계로 설치를 포기한 결과가 아니라, 현재의 단순 배치·정적 조회·단일 운영 장비라는 범위에서 추가 운영 비용을 정당화하지 못한다는 판단이다.

세 도구를 실제 미니 PC에 설치해 비교 부하 시험을 한 것은 아니다. 따라서 “도입하면 반드시 OOM”, “Kafka는 최소 몇 GB”, “현재 구조가 몇 배 빠름” 같은 수치는 제시하지 않는다. 미니 PC 사양은 판단의 한 축이고, 더 직접적인 이유는 **해결할 문제가 현재 경로에 있는가**이다.

## 8. 실시간 요구는 어떻게 이어가야 하는가

### 8.1 화면 갱신과 데이터 최신성은 다르다

현재 저장소 cron은 UTC 19:00, 즉 KST 04:00의 일일 적재·빌드를 의도한다. 실제 장비의 cron 배포와 시간대 적용은 별도 운영 확인 대상이다. 브라우저는 보이는 동안 60초마다 새 빌드를 확인한다. [cron 템플릿](../bootstrap/cron.d/poposafari), [화면 코드](../dashboard/public/app.js)

```text
이벤트 발생 → 서버 아카이브까지 대기
           → 미니 PC 다음 적재까지 대기
           → 적재·집계·게시 실행
           → 브라우저 다음 확인까지 대기
```

서버의 현재 아카이브 주기는 이번 작성에서 확인하지 않았다. 따라서 전체 지연을 정확한 숫자로 보장할 수 없다. 분명한 것은 **일일 적재 구조에 60초 폴링을 붙여도 이벤트 기준 60초 실시간이 되지 않는다**는 점이다. 서버 아카이브가 즉시 도착하더라도 다음 배치까지 거의 하루 기다릴 수 있다.

### 8.2 먼저 서버 개발자와 합의할 항목

1. “실시간”의 목표를 이벤트 발생부터 화면 표시까지의 p95 지연으로 정의한다.
2. 초당 이벤트 수, 피크, 일일 원본·압축 크기를 측정한다.
3. 누락·중복·순서 역전·지연 도착을 어느 수준까지 허용할지 정한다.
4. 서버와 미니 PC가 각각 중단됐을 때 보관 위치와 복구 방법을 정한다.
5. 안정적인 이벤트 ID·발생 시각·연결 키·스키마 버전을 합의한다.
6. 실시간 숫자를 잠정값으로 보여줄지, 배치 대사 후 확정할지 정한다.

### 8.3 가능한 확장 순서 — 아직 미구현

| 요구 수준 | 검토 방향 | 남는 과제 |
| --- | --- | --- |
| 하루 단위 추세 | 현재 배치 유지 | 장애 알림·백업·데이터 품질 강화 |
| 수 분 단위 가시성 | 서버 아카이브 주기 확인 후 마이크로배치 검토 | 적재·전체 DB 백업·집계 시간이 주기보다 짧아야 함 |
| 수 초 단위 이벤트 | 서버 이벤트 전달 + 소비자·조회 경로 설계 | 전달 보장, 중복 제거, 윈도 집계, 인증 |
| 다수 독립 소비자·재생 | Kafka 등 지속 가능한 이벤트 로그 검토 | 장비 분리, 보관·복제·소비 지연 운영 |

마이크로배치 전환도 cron 숫자만 바꾸면 끝나는 것은 아니다. 매 실행의 DB 독립 복사와 상세 파일 생성·보관 비용이 빈도에 비례해 증가한다. 상세 버전은 현재 최소 7일 및 최근 두 빌드를 보관하므로, 하루 한 번과 분당 한 번의 디스크 사용량은 크게 다르다.

SSE·WebSocket은 마지막 화면 전달 수단이다. 앞단 수집이 배치이면 push 연결을 추가해도 원본의 최신성은 개선되지 않는다.

## 10. 단순한 구조에 남아 있는 위험

### 10.1 원본 아카이브의 유실은 downstream에서 복구하지 못한다

README에는 서버의 export와 DELETE가 별도 세션이고, 그 사이 커밋된 행이 아카이브 없이 삭제될 수 있다는 기존 관측이 있다. 이번에는 서버 코드를 재검증하거나 수정하지 않았다.

대사는 아카이브와 로컬의 불일치 및 ID 갭을 탐지하는 단서가 되지만, **ID 갭 자체가 반드시 유실 증명은 아니다.** DB 시퀀스는 롤백 등으로도 비연속일 수 있다. 아카이브에 한 번도 기록되지 않은 이벤트를 미니 PC가 되살릴 수는 없다.

서버 측 해결은 단순히 “같은 세션으로 옮긴다”가 아니라, 실제 export·업로드 검증한 행과 삭제하는 행의 집합을 일치시키고 실패·재시도를 설계하는 일이다. Kafka 추가만으로도 이 원자성 문제가 자동 해결되지는 않는다.

### 10.2 로컬 백업은 장비 장애 백업이 아니다

기존 기록상 R2 `audit/` 보관 기간은 365일이다. 삭제된 과거 아카이브를 재구축으로 복원할 수 없고, 같은 디스크의 `.prev`도 디스크 장애에는 함께 사라진다.

아카이브 보존 연장 또는 별도 위치의 DB·Parquet 백업을 결정해야 한다. 현재의 독립 복사는 직전 상태 복구에 도움이 되지만 장기 보존·오프사이트 백업·고가용성을 대체하지 않는다.

### 10.3 가명 계정 ID도 접근 제한 대상이다

IP는 적재에서 제외하고 URL 등은 뷰에서 노출을 줄이지만, 원본 `detail` 전체가 완전히 익명화된다고 볼 수 없다. 대시보드 파일에는 계정 ID와 활동 건수가 포함된다.

현재 전제는 인증 없는 LAN/Tailscale 내부 운영자용 접근이다. 네트워크에 접근 가능한 사람은 화면뿐 아니라 상세 JSON도 직접 읽을 수 있다. 검색창이나 페이지 이동은 접근 통제가 아니다. 공개하려면 인증·권한·TLS와 상세 데이터 보관 정책을 별도로 설계해야 한다.

### 10.4 단일 장비라는 한계는 의도적으로 수용했다

미니 PC가 꺼지면 적재와 화면 제공이 중단된다. 재시도 가능한 배치와 기존 파일 보존은 복구를 쉽게 할 뿐, 무중단 서비스를 만들지 않는다. 업무상 허용 중단 시간이 짧아지면 도구 추가보다 장애 도메인 분리가 먼저다.

## 11. 프로젝트 설명용 요약

> 저는 기술 스택을 먼저 정하기보다 입력 데이터의 형태, 최신성 요구, 운영 자원을 기준으로 설계했습니다. 기존 서버가 R2에 로그 파일을 보관하고 있었고, 이번 작업은 서버를 변경하지 않는 범위였기 때문에 미니 PC의 DuckDB 배치 분석과 정적 대시보드를 선택했습니다.
>
> 약 8GB RAM의 Celeron N3150 장비에서 Airflow·Kafka·Redis를 실행하는 것이 불가능한 것은 아닙니다. 다만 현재는 작업 의존성이 단순하고, 입력이 파일 배치이며, 조회도 미리 계산한 JSON이므로 각 도구의 핵심 이점을 충분히 활용할 구간이 없었습니다. 대신 객체 단위 증분 처리, 데이터와 처리 이력의 트랜잭션, 독립 백업, 버전 기반 원자적 게시에 집중했습니다.
>
> 유저 상세 기능에서는 단순히 ID를 보여주는 것보다 지표의 계산 참여자와 목록을 일치시키는 일이 중요했습니다. 같은 DB 스냅샷에서 집계와 상세를 생성하고, 전체 목록은 필요할 때만 읽게 했습니다. 성능도 모든 항목이 개선됐다고 포장하지 않고, 재읽기 감소와 안전성·메모리 비용을 함께 기록했습니다.
>
> 현재 구조는 실시간 시스템이 아닙니다. 이벤트 기준 지연 목표와 서버의 전달 보장이 합의되면 마이크로배치 또는 스트리밍으로 확장하고, 그때 필요한 역할에 맞춰 Kafka·Redis·Airflow 도입을 다시 판단하는 것이 다음 단계입니다.
